## Descobertas da pesquisa (2026-09-26)

- **Obscura**: Apache-2.0 (gratuito). É um browser **sem janela**, feito em Rust, que fala o protocolo do Chrome (CDP) e funciona com Puppeteer e Playwright. Tem binário Windows na release v0.2.3. Serve para o agente **ler** a web e para mostrar a navegação dentro do app. **Não** substitui o Chrome quando o André quer ver um vídeo: a reprodução de mídia pode não funcionar.
- **AuK**: MIT (gratuito, inclusive os pesos). É **geração** de voz (fala), não reconhecimento. Então substitui a Piper na **saída**; NeMo/Whisper continuam na entrada. Roda sem Python pelo `audio.cpp` (tem build Windows com CUDA). Os exemplos oficiais são só em inglês e chinês: **o português precisa ser testado** (Task 1 do plano §13). Precisa de ~6 GB de vídeo, então descarrega o Ollama antes de falar, como já acontece na geração de imagem.
- **§14, as três referências são gratuitas**:
  - **obsidianui.dev**: biblioteca de componentes open source, licença **MIT**.
  - **bencho.dev**: blocos de interface interativos com licença **MIT** (o site, o nome e as fotos não entram). Blocos que servem direto ao app: *Action node*, *Canvas toolbar*, *Command bar*, *Radial menu*, *Slide to confirm*, *Inline confirm*, *Progress ticks*, *Notify*.
  - **designspells.com**: galeria **gratuita** de detalhes de design (só pede e-mail para a newsletter). Não distribui código: serve como inspiração, sem copiar.

## §14: análise das referências (sem código ainda)

1. Abrir os três sites e anotar, para cada tela do Open Assistant (Chat, Node Editor, Agentes, Configurações), 2–3 ideias que caibam no `DESIGN.md` atual. Prioridade para o Node Editor e a tela Agentes, que o §11 vai mexer.
2. De bencho.dev e obsidianui.dev (MIT), escolher no máximo 3 blocos para adaptar (candidatos: *Action node* para os nodes, *Command bar* para a paleta de nodes, *Inline confirm* para as confirmações do agente). Ao copiar código, manter o aviso de copyright MIT num comentário no arquivo.
3. Não copiar fotos, nome nem marca desses sites.
4. Registrar as escolhas em `docs/superpowers/specs/2026-09-2x-referencias-design.md` e marcar o §14 no ROADMAP.

## §11 fase 2: todo o sistema visível (plano a escrever depois da fase 1)

Usa o `traceSystem` da fase 1 para instrumentar o que já existe, **um fluxo do sistema por automação**:
- roteamento do chat (ação pronta sem tokens `matchAction` → agente → ferramenta `controlar_computador`);
- calculadora do app;
- agente do PC (cada ferramenta chamada vira uma etapa acesa);
- MCP (qual servidor e qual ferramenta foram chamados);
- voz (microfone → transcrição → resposta → fala; inclui o AuK do §13);
- geração de imagem (descarrega o Ollama → sd.cpp → imagem salva);
- leitura de páginas pelo Obscura (§12).

Também entram:
- **trilha por conversa**, filtrando as "Execuções recentes" pela conversa aberta, com um atalho no chat;
- guardar o histórico em disco;
- **fluxos do sistema por conversa**: hoje o canvas mostra só a última execução; a ideia é escolher uma execução do histórico e ver o que passou em cada node.

## §11 fase 3: "Sonhos" (plano a escrever depois da fase 2)

- Workflow do sistema **Sonhos**, rodando à noite por agendamento (reaproveitar o `trigger.schedule` e o agendador existente, com horário fixo em vez de "a cada X minutos").
- Etapas: ler as memórias e conversas do dia → modelo local propõe skills (formato SKILL.md) e conectores (MCP) → **fila de revisão** em Agentes do sistema → o André aprova → ativar.
- Nada é ativado sem aprovação (mesma política de segurança do agente).
- Formato único de workflow (nodes + ligações em JSON) já é o `WorkflowDoc` atual; a fase 3 só formaliza o "exportar/importar" de fluxos do sistema como modelo para o usuário copiar e editar.
